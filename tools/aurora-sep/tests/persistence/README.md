# SEP host-file publication fault tests

The atomic suite compiles the production C replacement primitive, Rust StoreFile wrapper, catacomb writer, enrollment preflight, delete preflight and owner-preparation flow against a synthetic per-file VFS. It checks short writes, allocation/open/security/chmod/close/rename/fsync failures, preservation of the old generation before rename (the temporary is closed before rename, so a close-time flush error is reported first), and a complete visible generation after a failed directory fsync. The C boundary tests reject symlinks and non-regular destinations, cover leftover temporary files and unsafe cleanup, and check that the writer holds its lock while it writes, syncs, renames and cleans up. They also cover `sep_store_replaceable()` and `sep_store_publishable()`: bind-mounted, non-regular, symlinked, or unremovable destinations, unmapped creator IDs, parents lacking directory fsync/rename/unlink support, append-only/dead/unwritable parents, read-only mounts, and non-regular or unremovable reserved temporary entries are refused without mutating the directory, and enrollment, delete and owner-preparation tests assert refusal before enclave commands on the modeled static refusals. The suite also compiles a deliberate regression and requires its named behavioral assertion to fail. No real files, SEP state or hardware are opened.

Run `python3 -I tools/aurora-sep/tests/persistence/persistence-tests.py --suite atomic --output /tmp/sep-atomic`. CI pins Rust 1.85.0. These host fixtures do not establish power-loss durability on physical storage or SEP anti-replay safety.

Each catacomb is replaced through a fixed temporary name, `/var/lib/.<name>.new`, which the SELinux module labels `aurora_sep_state_t` at creation like the catacomb itself; rename keeps that label. A crash after temporary-file creation and before rename can leave that file, up to 1 MiB plus the 16-byte header. Ordinary error paths unlink their own temporary file. The `.<name>.new` names are reserved for the driver. The next replacement of the same catacomb, serialized by a driver lock, unlinks a regular file left at that name, or finds it already gone, and creates it again exclusively; it never adopts or truncates one. Anything else at that name is left alone and the save fails. These files can contain biometric material. Successful publication leaves no temporary file.

The new file is created under kernel credentials and is published with mode 0600 whatever the calling task's umask: when the umask cleared bits, the driver sets the mode before writing. It takes its label and ownership from creation, not from the file it replaces. Truncation in place previously kept the existing inode's owner, mode, ACLs and extended attributes.

Only full-file replacement is implemented here. Header-tail copying and exclusive destination creation belong with their later callers and tests; this suite does not claim to exercise those operations.
